## 1. 무엇이 문제였나

소진공 스냅샷에 가게가 수록되는 시점이 밀리면서, 개업 수가 특정 분기에 몰렸다.

```
2024Q3    101곳
2024Q4  9,090곳     ← 90배
```

현실의 개업 현상이 아니라 제공처의 일괄 재동기화다.

**폐업 쪽 갭필링으로는 고칠 수 없다.** 갭필링은 `0 < gap <= threshold` 조건으로
"사라졌다가 **다시** 나타난" 구간만 메운다. 개업은 처음 등장한 시점이 문제라
메울 앞쪽 기록이 아예 없다. 방향에 따라 결함의 구조가 다르다.

`build_dataset.py:99` 주석에도 잔여 스파이크가 남아 있다고 적혀 있다(4106→2491→1443).
threshold 11은 최소화한 값이지 제거한 값이 아니다.

**보정 방식** — 첫 등장 분기 대신 **인허가를 받은 분기**를 개업 시점으로 재배정한다.

| 대상 | 처리 |
|---|---|
| 인허가 매칭 82.7% | 첫 등장 이전의 가장 최근 인허가 분기로 재배정 |
| 인허가가 관측 창(2020Q4) 이전 | 늦게 수록된 기존 점포이므로 개업에서 제외 |
| 미매칭 17.3% | **원본 첫 등장 분기 유지** — 추정을 넣지 않는다 |

결과:

```
              변동계수    범위
원본            0.925    0.00 ~ 23.20%
보정            0.500    0.00 ~  8.97%
보정 + ma4      0.170    2.00 ~  5.07%
```

## 2. 추가된 컬럼과 사용 규칙

| 컬럼 | 의미 | 쓰는 곳 |
|---|---|---|
| `개업_율_평균` | **원본.** 첫 등장 기준 | 이력 보존용. **분석·화면에 쓰지 말 것** |
| `개업_율_보정` | 인허가 재배정 적용 | 중간 산출물 |
| `개업_율_보정_ma4` | 위 값의 4분기 이동평균 | **상권 유형 분류는 이걸 쓴다** |
| `폐업_률_ma4` | `폐업_률_평균`의 4분기 이동평균 | 유형 분류 y축 |
| `개업_보정_매칭률` | 셀별 인허가 매칭 비율 | 품질 지표. 낮으면 해당 셀 보정 신뢰도 낮음 |

`개업_율_평균`은 **삭제하지 않는다.** 보정 전후 비교가 보고서 방법론 절의 근거다.

### 반드시 지킬 것 — 개업률 절대 수치를 화면에 띄우지 않는다

보정을 하면 최근 분기 개업률이 **구조적으로 낮게** 나온다.
2025Q4에 인허가를 받은 가게는 2026Q1 스냅샷에 등장하는데 데이터가 2025Q4에서 끝나므로
영영 잡히지 않는다. 실제로 2025Q4 보정 개업률 중앙값은 0.00%다.

그런데 **상권 유형 분류에는 영향이 없다.** 분류가 각 분기 중위값 기준 상대 판정이라
모든 셀이 같이 내려가면 상대 위치는 그대로다. 최신 분기에서도 정상 분류된다.

```
정상          "이 상권은 고회전 유형입니다"
쓰지 말 것     "이 상권의 개업률은 2.0%입니다"
```

## 3. 파이프라인 재실행 순서 ★ 가장 중요

```bash
python ai/build_dataset.py
python ai/fix_opening_rate.py      # ← 새로 추가된 단계
python ai/train_model.py
python ai/build_risk_index.py
python ai/import_normalized_db.py
python ai/build_explanations.py
```

> ### 경고
> `build_dataset.py`는 `final_dataset.csv`를 **통째로 새로 쓴다.**
> 그 직후 `fix_opening_rate.py`를 돌리지 않으면 보정 컬럼 4개가 사라지고,
> 상권 유형 분류가 조용히 실패하거나 엉뚱한 값을 낸다.
> **두 명령은 한 쌍이다. 하나만 돌리지 않는다.**

> ### 컬럼을 또 추가하게 된다면
> `final_dataset.csv`에 컬럼을 추가하면 `ai/import_normalized_db.py`의
> `_supplement_score_only_cells()`가 영향을 받는다. 이 함수는 직전 분기가 없어 비율을 못 구한
> 최신 예측 셀을 점포수만 살려 끼워 넣는데, 그때 나머지 컬럼을 NaN으로 채워야 하기 때문이다.
>
> 2026-08-20에 실제로 여기서 `KeyError`가 났고, 지금은 `commercial`의 스키마를 보고
> **없는 컬럼을 자동으로 NaN 처리**하도록 고쳐서 같은 문제가 재발하지 않는다.
> 다만 컬럼 추가 후에는 `python ai/import_normalized_db.py`를 한 번 돌려 확인할 것.

### fix_opening_rate.py 동작

| 항목 | 값 |

보고서에 실린 숫자는 전부 그대로다.** 바뀌는 것은 화면 표시와 상권 유형 분류뿐이다.

## 4. 원본 데이터 준비

`build_dataset.py`와 `fix_opening_rate.py`만 원본이 필요하다. 나머지 단계는 CSV만 있으면 된다.

### 4-1. 필요한 폴더는 둘뿐

```
<원본폴더>/소상공인시장진흥공단_상가(상권)정보_분기별데이터/   분기 zip 21개
<원본폴더>/화성시_인허가데이터/                              csv 12종
```

카드매출·유동인구·KOSIS는 `eda/` 노트북에서만 쓴다. 파이프라인 실행에는 필요 없다.

### 4-2. 폴더 이름이 사람마다 다르다

`eda/paths.py`가 이 차이를 흡수한다. 아래 순서로 찾는다.

```
1. 환경변수 RAW_DATASET_DIR (있으면 그대로 사용)
2. <RAW_DATA_DIR>/hwaseong-commercial-dataset
3. <RAW_DATA_DIR>/Hwaseong-commercial-ai-main-dataset
4. <RAW_DATA_DIR> 자체
```

### 4-3. `.env` 설정

원본 폴더를 **리포 루트 안에** 두는 경우 (`.gitignore`에 이미 등록돼 있어 커밋되지 않는다):

```
RAW_DATA_DIR=.
```

리포 밖에 두는 경우:

```
# Windows
RAW_DATA_DIR=D:/hwaseong

# macOS
RAW_DATA_DIR=/Volumes/SSD/hwaseong-commercial
```

폴더 이름이 위 후보 어디에도 안 맞으면 직접 지정한다.

```
RAW_DATASET_DIR=D:/어디든/내폴더명
```

> README와 `팀원-DB-셋업.md`에 "외장 SSD 원본이 필요하므로 `build_dataset.py`는 돌리지 않는다"고
> 적혀 있는데, 이는 원본을 외장 SSD에 둔 팀원 기준 문장이다.
> 원본을 갖고 있다면 어느 OS에서든 돌아간다.

## 5-1. 모델 성능 수치 — 두 가지를 섞지 말 것

`train_model.py`가 출력하는 수치와 실험 문서에 적힌 수치는 **측정 조건이 다르다.**

| 출처 | 조건 | 스피어만 | 리프트 |
|---|---|---|---|
| **`train_model.py` 실행 결과** | 고정 분할 1회 (TRAIN_END 2023Q2 / VALID_END 2024Q2) | **0.4184** | **1.433x** |
| 내부 검증 실험 | 테스트 구간 3개를 옮겨가며 측정 | 0.5016 | 1.522x |

**보고서·발표·대외 자료에는 위쪽(0.4184 / 1.433x)만 쓴다.**
아래쪽은 feature 선택 근거를 비교하기 위한 내부 수치이고, `train_model.py`를 그냥 돌려서는
재현되지 않는다. 재현이 안 된다고 버그로 오해하지 말 것.

## 6. 자주 겪는 문제

| 증상 | 원인 · 해결 |
|---|---|
| 컬럼이 8개만 나온다 | `git pull` 안 받았거나, `build_dataset.py`만 돌리고 `fix_opening_rate.py`를 빠뜨림 |
| `FileNotFoundError: store_panel.csv` | 이 파일은 커밋되지 않는다. `build_dataset.py`를 먼저 돌려야 생긴다 |
| 인허가 매칭률이 0% | `.env`의 `RAW_DATA_DIR`이 틀림 → `python -c "import sys; sys.path.insert(0,'eda'); import paths; print(paths.PERMIT_DIR, paths.PERMIT_DIR.exists())"` |
| `UnicodeDecodeError` | 인허가 CSV 인코딩. 스크립트가 cp949 → utf-8 순으로 시도하므로 파일이 깨진 경우다. 다시 받는다 |
| 개업률이 전부 0 | 인허가 폴더는 찾았으나 `지번주소`/`인허가일자` 컬럼이 없는 파일만 있음. 파일 구성 확인 |
| 유형 분류가 한쪽으로 쏠린다 | 고정 임계값을 쓴 경우다. **각 분기 중위값** 기준이어야 한다 |
| `import_normalized_db.py`에서 `KeyError` | `final_dataset.csv`에 컬럼을 추가한 뒤 임포터를 안 맞춘 경우. 현재 코드는 자동 처리한다 |
| 스피어만이 0.50이 안 나온다 | 정상이다. 5-1절 참조 — 고정 분할 기준은 0.4184다 |

## 7. 알려진 한계 — 보고서에 그대로 적을 것

1. **매칭률 82.7%.** 인허가 12종이 음식점·미용업·약국 위주라
   소매·부동산·교육 업종은 인허가 대상이 아니어서 보정할 수 없다
2. **주소 단위 매칭.** 같은 주소의 여러 업체를 완전히 구분할 수 없다.
   "첫 등장 이전의 가장 최근 인허가"로 개선했으나 근사치다
3. **"인허가 = 개업" 가정.** 인허가 후 개업하지 않거나 몇 달 뒤 여는 경우가 있다.
   지연 0~1분기가 48.8~60.5%인 것으로 보아 대체로 성립한다
4. **2024Q4는 보정 후에도 최고치**(3,017 / 평시 1,264~1,766). 잔여 이상이 남는다.
   기존에 확인된 "2024Q4 폐업 잔여 이상치 9,090건 미해소"와 같은 뿌리로 보인다
5. **최근 분기 개업률은 구조적으로 과소 추정된다**(2번 절 참조). 절대 수치를 쓰지 않는다

### 발표·보고서용 한 문장

> 폐업 방향의 데이터 결함은 갭필링으로, 개업 방향의 결함은 인허가 재배정으로 교정했다.
> 두 방향은 결함의 구조가 달라 같은 방법으로 처리할 수 없었다.

## 8. 데이터 취급 주의 (재확인)

- `data/raw/`와 원본 데이터셋 폴더는 **커밋하지 않는다.** `.gitignore`에 등록돼 있다
- `store_panel.csv` · `store_train_table.csv` · `store_labels.csv`는 상가업소번호·지번주소·좌표를
  담고 있고 이 리포는 **공개 저장소**다. 예외 목록에 추가하지 않는다
- 리포에 포함된 6개 파일은 전부 읍면동×업종 집계 단위다
- 행정데이터 원본을 외부 AI API로 전송하지 않는다(공모전 규정, 위반 시 실격)
